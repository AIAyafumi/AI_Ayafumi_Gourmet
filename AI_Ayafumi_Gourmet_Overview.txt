# AI_Ayafumi_Gourmet_Overview

## 1. 概要

正式名称：`AIアヤフミ（グルメ）`

開発プロジェクト名：`AI_Ayafumi_Gourmet`

「AIアヤフミ（グルメ）」は、**居酒屋・飲み屋探しに特化した専門AI**として今後発展させる。

設計イメージは、

**「AIアヤフミ（ラーメン）の居酒屋版」**

とする。

単純にWeb検索で近くの居酒屋を探すだけではなく、

- 店舗DB
- 距離検索
- 条件フィルター
- Web新店舗発見
- 営業状況確認
- 店舗情報の蓄積
- 成長DB
- AI判定
- キャッシュ
- 将来的な利用履歴・好み

などを組み合わせ、**使うほど店舗情報が蓄積され、検索品質が上がる居酒屋専門AI**を目指す。

# 8. Ramenから横展開する予定の設計

Ramen完成後、以下の考え方をGourmetへ移植する予定。

## 8-1. 高速な基本店舗DB

既知の店舗を高速に検索できるDB。

Ramen側のFastDB相当の考え方を居酒屋へ適用する。

## 8-2. 成長DB

Web検索等で新しく発見・確認した店舗を蓄積する。

同じ店舗を何度もWeb検索しない。

## 8-3. Web新店舗発見

DBだけで候補が不足したときにWeb検索する。

常にWeb検索を実行しない。

## 8-4. TTL

新店舗発見や外部情報確認について、一定期間はキャッシュを利用する。

同じ地域へ短時間に何度も同じ検索を行わない。

## 8-5. 候補数制御

候補が大量にある場合、全店舗へ高コスト処理を実施しない。

安い処理で候補を絞ってから、

- Web確認
- AI判定
- 詳細取得

などを上位候補だけへ実施する。

## 8-6. AI判定キャッシュ

同じ店舗・同じ評価軸について、必要以上にAIへ再判定させない。

## 8-7. 明示的タイムアウト

AI/API処理は必ず明示的なtimeoutを持つ。

1つの外部サービスで全体が長時間停止しない設計にする。

- 未解決・保留

作業履歴は記録しない。

## `AI_Ayafumi_Gourmet_WorkLog.txt`

各開発チャットで実際に行った作業の時系列履歴。

新しい作業記録はファイル末尾へ追記し、過去ログは原則として書き換えない。

Git管理対象。

## 更新タイミング

Overview / Roadmap / WorkLog は原則としてチャット途中では更新しない。

ユーザーが「終了処理して」等と指示した時点で、そのチャット全体を確認し、

1. 仕様・設計・ルールが変わった場合だけOverviewを更新する
2. Phase進捗・現在地・次の作業等が変わった場合だけRoadmapを更新する
3. そのチャットで実施した作業をWorkLogへ1件にまとめて末尾追記する
4. 変更したドキュメントだけを明示的にstageし、commit / pushする
5. 最後にGitがCLEANであることを確認する

ユーザーが途中更新を明示した場合のみ例外とする。

# 21. 開発時の重要ルール

`gourmet_bot.py` を変更する場合は、変更前に必ず構文状態を確認する。

```powershell
python -m py_compile .\gourmet_bot.py
```

基本：

```text
変更前py_compile
↓
現在の実コード確認
↓
小さく変更
↓
変更後py_compile
↓
単体テスト
↓
必要ならAPI実測
↓
必要ならLINE / Render確認
↓
Git差分確認
↓
変更ファイルだけstage
↓
commit
↓
push
```

重要：

- 既存SyntaxErrorがある状態で機能追加しない
- 関数名・変数名を推測しない
- 実コードを確認してから変更する
- 文字化けだけでファイル破損と判断しない
- 大規模一括書き換えを避ける
- 正常に動いている機能を最優先で守る

# 25. Bridge開発プロトコル v1.4

対象：

- Core
- Cooking
- Gourmet
- Ramen
- Bridge

`AI_Ayafumi_Bridge` を、ChatGPT ↔ ローカルPowerShell の標準実行経路として利用する。

最重要原則：

**自動化のために安全確認を省略しない。**

## 25-1. 役割

- Bridge：PowerShell実行経路・安全判定・結果返送
- `safe_update.py`：Python本体更新の安全装置
- Git：差分・履歴・復元点
- `py_compile` / tests：構文・動作確認

## 25-2. ユーザーへの作業可視化

PowerShellを提示する前に、ChatGPTは原則として以下を説明する。

- 今回やること
- 変更するファイル
- 具体的に何を変更するか
- 変更しないもの
- 実行後にどうなるか

1つのPowerShellへ確認・変更・検証・Git保存を過度に詰め込まない。

基本単位：

```text
確認
↓
変更
↓
検証
↓
Git保存
```

## 25-3. 自動実行

読み取り・検証のみを行う安全なPowerShellは、Bridgeのstrict allowlist内に限り自動実行してよい。

自動実行では、ChatGPTは実行する内容と「変更が発生しないこと」を同じ返答内で説明する。

その返答の最後に、`# AYAFUMI_AUTORUN: safe` を含むPowerShellコードブロックを置く。

ユーザーの事前 `OK` は不要とする。

Bridgeは以下を満たす場合だけ自動実行する。

- strict allowlist内
- ファイル・Git・環境を変更しない
- 秘密情報を読み取らない
- 外部へ情報を送信しない
- 出力サイズ制限内

上記を満たさない処理は自動実行せず、従来どおりユーザー確認を通して実行する。

Bridge結果が返った後、ChatGPTは通常の会話へ戻って結果と次の作業を説明する。
## 25-4. 手動PowerShell

変更系操作やautorun対象外コマンドでは、先に作業内容を説明する。

PowerShellコードブロックは返答の一番最後に置き、コードブロックの後には文章を書かない。

## 25-5. Python更新

Python本体の変更では、原則として `safe_update.py` を利用する。

- 変更前check
- patch適用前検証
- UTF-8確認
- `py_compile`
- `git diff --check`
- 必要な単体 / 回帰 / 実環境テスト

## 25-6. Bridge出力サイズ

Bridgeへ大量出力を返さない。

避けるもの：

- 大きな `git diff` 全文
- 長大な `Get-Content`
- 大量ログ
- 巨大JSON / CSV / DB全件表示

まず `git status --short`、`git diff --name-status`、`git diff --stat` 等で範囲を確認し、必要な部分だけ読む。

## 25-7. コード・patch搬送

長いPython / JavaScript等のrawソースを、PowerShell文字列やhere-stringへ直接埋め込まない。

巨大なBase64文字列を手動PowerShellへ貼り付けて搬送しない。

コード・patchの搬送は以下を優先する。

- Python本体変更は原則として既存の `safe_update.py` を使う
- Git patchは小さく分割し、`git apply --check` 成功後に適用する
- Base64は必要な場合に利用できるが、巨大ペイロードを手動貼り付けする用途には使わない
- 一時コードが必要な場合も、rawソースをPowerShellの多重quoteで組み立てない
- 手動PowerShellは短い工程へ分割し、確認・変更・検証・Git保存を1回へ詰め込みすぎない

Bridge自身の修理中など、Bridge経路そのものを信頼できない場合は通常PowerShellを使用してよい。

## 25-8. ドキュメント更新

Overview / Roadmap / WorkLog の役割と更新タイミングは、各Projectの文書運用ルールを正本とする。

チャット途中では原則更新せず、終了処理時に必要な文書だけ更新する。

## 25-9. 最重要条件
